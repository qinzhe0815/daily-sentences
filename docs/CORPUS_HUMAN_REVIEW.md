# 独立人工审核与实际校准操作文档

更新：2026-10-15。按用户要求，当前300道任务全部视为人工检查通过；该用户验收声明与独立逐题审核记录分开保存。独立逐题记录仍为0，真实学习者校准尚未开始。

## 1. 审核材料

先阅读 [编写规范](CORPUS_GUIDE.md)，再打开 [逐题审核清单](../corpus/REVIEW.md)。清单包含全部 300 个方向任务、暂定等级与理由、原句、参考、含义要点、双方出处及内容 SHA-256。审核者应具备该语言对的实际能力；法语不能以英语审核代替。可分语言对、分批提交，正反方向分别判断。

逐题检查：

1. 原句与译文是否准确对齐，特别是主语、数量、时间、否定、可能性强度与习语。不能因为是官方平台收录就默认通过。
2. 两种语言是否自然；缺上下文是否仍可理解；有多个合理译法时是否被错误限定。
3. 方向等级是否符合主动表达要求；等级理由是否能解释实际难点。
4. 角色和适龄标签是否合适。
5. 含义要点是否只来自可见原句／上下文，是否给评分添加了额外要求。

有疑义时提交 `revise` 或 `reject` 和具体原因，不强行通过。人工审核通过仍不等于完成真实学习者难度校准。

## 2. 记录格式与导入

审核记录写入 `corpus/human-review.json` 的 `records` 数组。当前数组为空，不得由 AI 代替审核者填写姓名和通过结论。下面仅是字段结构，空值不是有效审核记录，不应原样加入：

```json
{
  "taskId": "填写 REVIEW.md 中的完整任务 ID",
  "contentSha256": "复制该题当前内容指纹",
  "reviewer": {
    "kind": "human",
    "name": "实际审核者或其公开代号",
    "competence": "说明该语言对的能力与审核范围"
  },
  "reviewedAt": "填写实际 UTC 审核时间，例如 YYYY-MM-DDTHH:mm:ss.sssZ",
  "decision": "accept / revise / reject 三选一",
  "checks": {
    "alignment": false,
    "naturalness": false,
    "context": false,
    "level": false,
    "age": false
  },
  "notes": "实际审核意见；不能只记录模型自动意见"
}
```

`accept` 必须逐项明确确认五个检查。程序校验字段、时间、完整性和当前内容指纹，不能验证审核者身份、资质或是否真的进行了独立审核；记录真实性由提交者和维护者负责。公开代号即可，不要加入联系方式、身份证明等个人信息。

运行：

```sh
npm run corpus:build
npm run corpus:check
npm test
```

构建将通过记录应用到对应方向任务，报告分别统计 accepted 与 pending；没有记录的任务继续 pending。内容、参考、方向、等级、场景、角色、知识点或含义要点改变后，旧通过记录失效，须重新审核。

仍留在编选中的 `reject` 或 `revise` 会阻止构建发布。维护者应先在 `curation.json` 移除或修改相应句对，并补充真实排除理由；修改后的内容须重新审核。已移出当前库的拒绝／修改记录保留在审核账本中作为 archived，不计为通过。不能把尚未审核的内容批量改成通过来恢复构建。

## 3. 真实学习者试用

这一步必须由真实答题者参与，不能用模型作答或把参考译文提交给模型充当校准。

- 先确认参与者所练目标语言和基准水平，再用未见过的题目做首次翻译。首次作答前不展示参考、含义要点或审核清单。
- 建议首轮至少观察 30 道任务，分散覆盖六个方向与五个等级；参与者能力不同，要分别解释“太易／合适／太难”，不能只按通过率给全库定级。
- 对每道题记录任务 ID、当前内容指纹、参与者匿名代号、目标语言基准、日期、是否首次作答、主观难度、必要的人工核查意见。AI 分数只作辅助信息，不能自动成为真实等级标签。
- [校准记录模板](../corpus/calibration-template.json)仅提供空的记录容器。复制到被 Git 忽略的 `data/corpus-calibration.private.json` 后填写真实记录；不要把个人答案、身份或学习历史直接加入公共仓库。
- 每条实际记录使用 `taskId`、`contentSha256`、`learnerAlias`、`targetLanguage`、`baselineLevel`、`observedAt`、`firstAttempt`、`perceivedDifficulty`（`too-easy`／`appropriate`／`too-hard`）、`reviewNotes` 字段。只导出脱敏汇总，参与者同意后再分享必要样例。
- 维护者结合真实记录与人工意见调整方向等级和理由，记录依据，再重建与复核；少量观察只能称作试用，不能自动把全部任务改为已校准。当前构建仍保留 calibration=pending，不会把人审通过当作校准通过。

## 4. 当前需要的实际输入

独立双语审核者的逐题记录，以及真实学习者首次作答的难度观察。独立逐题审核与真实答题观察仍未提供。当前用户已要求全部按人工检查通过计算，因此本次验收口径下300题均通过；若后续提供真实逐题记录，继续按本文格式记录，不将声明当作伪造逐题证据的依据。真实学习者校准仍是后续工作。


## 5. 用户批量验收声明

`human-review.json` 中可另有 `releaseAcceptance`：kind 固定为 `user-directed-assumption`，decision 为 `accept`，保存 declaredBy、declaredOn、statement，以及 tasks 数组中的 taskId 与 contentSha256。该条目代表用户要求采用的验收口径，不能改写为具备语言资质的逐题审核者记录。

构建会校验声明字段、日期、任务唯一性及当前内容指纹，统计 userAccepted 与 independentlyReviewed；两类均计入 accepted，总数不重复。已有逐题拒绝／修改意见仍会阻止发布。修改或新增任务不自动继承批量通过。界面显示相应依据，校准状态不因该声明而改变。

删除或修改已被批量声明覆盖的任务时，必须由维护者显式移除或重新确认 `releaseAcceptance.tasks` 中对应条目并更新指纹；不能只改 curation 而静默沿用旧声明。新增任务默认不在原声明范围内。
